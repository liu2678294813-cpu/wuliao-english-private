## 失败记录与修正依据

完整 E2E 首轮实际结果为 253/259，六项失败。两项旧 tools-only 断言与现行“统一含文章”发行要求冲突；另三项业务测试在未优化的 `039c4d9` 工作树复现相同失败：刷新已保留词库路由、导入入口已移到首页、复习持久写入会刷新 iframe。修正测试前提，保留真实按钮、进度、复习日期和历史的断言，没有改这些业务功能。

扫描 PDF 的旧测试在精读页等待已移到首页的上传控件。测试改为首页导入、取消、重试及真实本地 OCR，继续检查十页来源、20 个完形空、四篇各五题、原图段落数 2/1/1/1、零结构错误与零提前保存。修正后的场景在优化前源码和最终完整套件均通过。

后续完整套件暴露一项笔测试的坐标稳定性问题，未优化源码也复现。既有阅读页会在初次布局后约 420ms 恢复滚动位置，旧测试只等两个动画帧，坐标落到题干而非可书写区域。只修正测试：先验证目标区域位置稳定，再执行唯一笔手势；仍要求抬笔前笔模式启用、恰好一条笔迹持久保存、收起及重载后的笔迹一致。修正后优化前源码连续 3 次通过，最终完整套件再次通过。失败时也释放指针，防止把按下状态带入其他场景。

全套 E2E 与 Android 大构建并行执行时还出现一次笔性能超时。最终完整套件使用单 worker，构建完成后再执行；未删测试、加重试或放宽性能阈值，未将这次环境负载推测当作已证实的业务根因。

生产门禁初次还因干净 worktree 缺生成目录与既有 OCR 对照图返回 ENOENT。创建生成目录、只读复用原 136 张对照图后，按原规则重跑通过，未改内容校验或例外清单。原词库目录中的 CRLF / LF 生成字节差异通过正式构建重新生成解决。

## 改善证据及不能据此推导的结论

优化前基线为真实 Git 源码 `039c4d9742140d9c2e15d316dd6bbde69a23ae55`；固定 15ms Mock 网络延迟。三个具体例子：

1. 同图识别两次后修改图片：网络请求 **3 → 2**，有效本地复用 0 → 1；测得 Mock 总耗时 93.78 → 61.57ms。修改图片仍发新请求。
2. 同一句子和译文用于两个 Attempt：网络请求 **2 → 1**，测得 Mock 总耗时 62.44 → 33.94ms；结果重新绑定当前 Attempt。生成新句子仍为 **2 → 2**。
3. 同篇文章不同阅读题：请求仍为 **2 → 2**，实际公共前缀 **1856 → 1930 字节**；同篇完形不同空格公共前缀 **856 → 1028 字节**。这是字节一致性证据，不是缓存 Token 命中证据。

相同短词切换模型时，请求 **1 → 2**：原来一次请求来自错误的跨模型结果复用，修复以正确隔离优先。首次、已有重复缓存、Endpoint 切换、force、取消重提均按本来的正确行为执行；未把原本已经好的场景包装成新增收益。

真实模型输入 / 读 / 写 Token、命中率、账单和推理质量均 **Unknown / 未验证**。没有有效价格卡时不显示精确节省；Mock 时间不代表真实服务商时间。九类 Provider 官方文档支持与真实付费命中仍是两层证据。
